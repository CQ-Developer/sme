## 1. 系统与信任边界

三个信任域：

| 域 | 内容 | 是否可信 |
| --- | --- | --- |
| **客户端进程** | 口令 → 长期身份密钥、Olm 账号与会话、10 条明文环形缓冲、UI | 假定可信（未越狱/未 root 的前提下） |
| **服务端** | 无状态网关 + 共享易失队列（密文 + from/to 元数据，TTL 24 小时） | **不可信**（零知识假设：它可以被入侵、被运营方窥探、被依法调取） |
| **网络** | 客户端 ↔ 网关（TLS/WSS）、网关 ↔ 队列组件 | **不可信**（首层 TLS 只提供传输保护，不承担端到端保证） |

身份锚点：**长期 Ed25519 身份密钥**，首次注册时随机生成、以口令派生 KEK 加密存于本地 keystore（见 `plan.md` §6.1）。Olm 账号密钥由它签名绑定。

## 2. 资产清单

| 资产 | 存在哪里 | 敏感性 | 备注 |
| --- | --- | --- | --- |
| 消息明文（含图片） | 仅两端进程内存 + 渲染瞬间的 UI 字符串 | 最高 | ≤10 条/端，图片另受 8MB 预算；退出即清；**永不落盘**（P1） |
| 长期身份私钥 | 本地 keystore（AEAD 密文） | 最高 | 泄漏后需生成新身份并让联系人重新核对安全码（§9 R11） |
| Olm 会话状态（双棘轮） | 本地 keystore（密文，随消息更新） | 最高 | 泄漏后可解密该会话**后续**消息；历史消息不存在 |
| Olm 账号私钥（含 prekey） | 本地 keystore（密文） | 高 | 同上 |
| 口令 | 仅用户记忆 | 最高 | 永不出网、服务端不存 |
| 口令盐 / Argon2id 参数 | 本地配置（无秘密）+ 服务端副本 | 低 | 本地副本使解密不依赖服务端 |
| One-time / fallback prekey 公钥 | 服务端（公开数据，短 TTL） | 低 | 公开数据，无保密要求 |
| 消息密文 | 网关与队列组件内存，≤24 小时 | 中 | 服务端不可解密；**不进入用户库** |
| 路由元数据（谁 → 谁、何时、长度、频率） | 服务端内存（队列组件） | 中 | **无法隐藏**，见 §7 |
| 通讯录 / 安全码 pin | 本地 keystore（AEAD 密文，D13′=B′） | 高 | 泄漏 = 社交图谱暴露，但不含任何消息 |

## 3. 安全目标

| # | 目标 | 由什么实现 | 验证方式 |
| --- | --- | --- | --- |
| **G1** | 服务端与网络中间人无法读取消息内容 | Olm 端到端加密（AES-256-CBC + HMAC-SHA256，密钥由 Curve25519 3DH + HKDF-SHA256 派生） | 集成测试：金丝雀字符串不出现在服务端任何存储/日志/内存转储（I1、I5） |
| **G2** | 消息完整性与来源可认证 | 双棘轮消息认证 + 登录用 Ed25519 签名；Ed25519 ↔ Curve25519 的绑定由服务端账号记录 + TOFU pin 承担，SAS MAC 对双方两把公钥一起校验 | 篡改密文 → 解密失败且不崩溃；pin 变更触发 I10 告警；SAS MAC 不匹配 → `SasFailed` |
| **G3** | 前向保密与后向保密（PCS） | 双棘轮 | 协议层测试：模拟密钥泄漏后，旧/新消息不可解 |
| **G4** | **磁盘上无消息留存**（密钥材料与用户信息以密文落盘） | 消息只存在于内存；退出时 `zeroize`；keystore 为 AEAD 密文 | I4、I6、I9（`i9_canary…` + I5）、I11 |
| **G5** | 服务端不长期留存**消息**（用户信息可持久化） | 密文队列 TTL 24 小时 + D-ack 即删 + 禁用持久化（I7）+ tmpfs；用户库无消息字段（I1） | I1、I7、I8、I9 |
| **G6** | 口令与私钥不出设备 | 登录用挑战-签名；口令派生只在本地 | 协议审计 + 网络抓包断言（无口令字段） |
| **G7** | 首次联系之后的密钥替换可被检测 | TOFU pin（keystore 加密保存，D27）+ 身份变更告警 + 交互式 SAS（7 个 emoji / 3 个十进制短码，D28，MAC 绑定双方身份密钥） | I10：pin 不被覆盖、变更事件被上报；SAS 状态机测试与真实网关 E2E |
| **G8** | 畸形输入不导致崩溃或状态污染 | 严格解析（拒绝未知字段、长度上限）+ fuzz | 对信封解析器跑 fuzz，断言 fail-closed |
| **G9** | **收发双方互相推断不到对方状态** | 无 E2EE-ack、无已读回执、无 presence 展示；图片同样走队列，不存在「在线直传」旁路；唯一回给发送方的失败是「服务器暂存已满」，与对方状态无关 | 协议测试：发送方可收到的唯一信号是 Q-ack；抓包断言无回执类消息 |
| **G10** | 图片不携带元数据（EXIF / GPS / ICC） | `sme-media` 压缩链路强制剥离；方向由像素旋转而非 EXIF 表达 | **I12**：对带 GPS 的样例图断言输出中无 EXIF 段与坐标字节 |

## 4. 信任假设

| # | 假设 | 若不成立会怎样 |
| --- | --- | --- |
| T1 | 设备操作系统与运行时未被攻陷（无 root/越狱、无键盘记录器、无截屏工具） | 一切保证失效 —— 明文在屏幕和内存里都是敞开的 |
| T2 | 口令强度足够 | 身份私钥可被离线暴力破解（见 §6 S4） |
| T3 | OS 提供的 CSPRNG 可信 | 会话密钥/随机性可预测，加密失效 |
| T4 | 用户会核对安全码 | 首次联系的中间人攻击无法关闭（见 §6 S1） |
| T5 | 第三方密码学库正确 | `vodozemac` / `ed25519-dalek` 的缺陷会直接破坏 G1–G3 |
| T6 | 队列组件按「无持久化」部署 | G5 被破坏（运维误配是这个项目最现实的失败模式之一，因此必须有 I7 启动自检） |

## 5. 对手模型

| # | 对手 | 能做到 | 做不到 |
| --- | --- | --- | --- |
| **A1** | 网络被动窃听者 | 看到密文、长度、时序 | 读内容 |
| **A2** | 网络主动 MITM（含恶意代理、TLS 终结者） | 阻断、延迟、丢包、注入垃圾 | 读内容、伪造有效密文（需要密钥） |
| **A3** | 服务端运营方 / 被入侵的网关 | 读全部元数据；丢弃/延迟/重排密文；在**首次联系**时替换密钥；离线时扣留消息 | 读明文；读历史（不存在）；替换已固定的对端密钥（会被签名/安全码识破） |
| **A4** | 拿到队列组件内存快照的运维/入侵者 | 读到 ≤24 小时的密文 + 元数据 | 解密内容 |
| **A5** | 拿到设备的攻击者 | 与登录后的现场状态等同：可读内存中的 ≤10 条消息与会话；可用会话继续收发 | 读磁盘上的历史（不存在）；离线解密已过去的会话 |
| **A6** | 设备上的恶意软件 / 截屏 / 键盘记录 | 一切 | —— 明确不在防护范围（§7） |
| **A7** | 元数据分析者 | 绘制社交图谱、活跃时间、消息量级 | —— 部分不在范围（§7） |
| **A8** | 恶意对端 | 发送畸形/超大/重放消息；冒充他人 ID 尝试投递 | 解密他人会话（无密钥） |
| **A9** | DoS 攻击者（已注册账号） | 灌满他人队列（上限 100 条）导致合法消息被丢弃；刷登录挑战 | 读内容；持久化任何东西（重启即清） |

## 6. 攻击场景演练

### S1 恶意服务端在首次联系时实施 MITM

- **过程**：用户 A 首次给 B 发消息，服务端把 A 的 prekey 换成自己的，同时把 B 的换成自己的。双方各自与「服务端」建立 Olm 会话。
- **结果**：**在用户核对安全码之前，攻击成立** —— 这是所有 TOFU 系统的固有窗口。之后一旦核对，安全码不匹配即暴露。
- **缓解**：① 安全码必须显眼地显示「未验证」状态，不能默认装作安全（TUI 已显示 TOFU 未验证）；② 提供二维码/短码核对路径（**已实现**：7 emoji / 3 个十进制短码 + 双方确认）；③ 首次联系后任何身份密钥变化都必须弹出告警，不能静默接受（**已实现**：pin 不覆盖 + `PeerKeyChanged` + 阻止发送）。
- **残余**：用户不核对就永远无法发现。

### S2 设备被扣押

- **过程**：设备在联网会话中被扣押。
- **结果**：攻击者拿到内存中的 ≤10 条消息、KEK，以及磁盘上的 **keystore 密文**（身份、会话状态、通讯录）。**磁盘上没有任何消息**，但弱口令可以在离机后慢慢破解 keystore。
- **缓解**：Argon2id 高参数 + 强制口令强度；空闲锁定与紧急擦除；`FLAG_SECURE` 防快照。
- **残余**：设备未锁屏时，屏幕上的内容就是当前对话；`zeroize` 只能覆盖我们自己的缓冲区，UI 框架的字符串副本无法保证擦除（§9 R2）。

### S3 队列组件被 dump

- **过程**：运维或攻击者对 Valkey/Redis 做 `SAVE`、core dump 或调试器 attach。
- **结果**：得到 **≤24 小时**窗口内的密文与 from/to 元数据，**无法解密**；且因禁用持久化 + tmpfs，攻击者拿不到跨重启的历史。
- **残余**：元数据暴露给额外的组件（`plan.md` §12.1 已声明）。

### S4 弱口令的离线暴力破解

- **过程**：攻击者拿到 keystore 文件（设备丢失、备份泄漏、同步目录被入侵），离线跑 Argon2id 字典攻击。盐与参数就在同一目录的本地配置里，无需服务端配合。
- **结果**：口令一旦被猜出，攻击者得到：身份私钥（可冒充身份）、通讯录与 pin、**当前会话状态**。但他**仍然拿不到任何历史消息** —— 因为消息从不落盘。
- **缓解**：① Argon2id 参数按现代基线取值（建议 m≥64 MiB、t≥3、p≥1，随硬件上调）；② 强制最小口令强度并提供强度提示；③ 文档明确写明「keystore 的安全性等于口令强度」。
- **残余**：这是本设计最锋利的一处取舍（§9 R11）。

### S5 重放与乱序注入

- **过程**：服务端（或 A8）把旧密文重复投递给接收方，或打乱顺序。
- **结果**：由棘轮消息序号与接收链状态拒绝重复；乱序在窗口内可正常处理，超出窗口则拒绝。客户端对失败一律 fail-closed：不进缓冲、不 ACK、不崩溃。
- **残余**：会话状态现在跨重启保持（D2 修订），因此重放窗口也跨重启延续，拒绝规则一致。

### S6 队列灌满导致消息丢失

- **过程**：已认证的攻击者持续给某个离线用户发消息，填满其队列配额（100 条、图片 ≤10 张/≤12MB）。
- **结果**：合法消息被丢弃，且因服务端不持久化**无法补救**。
- **缓解**：按发信人限流 + 队列按发信人配额 + 网关对异常行为告警；UI 如实显示「对方离线，消息可能丢失」。
- **残余**：可用性攻击无法根治，这是「不长期存储」的必然代价。

## 7. 明确不在威胁模型内

| 不在范围 | 原因 |
| --- | --- |
| 已被完全攻陷的终端（A6）、键盘记录、截屏、肩窥 | 终端即边界，超出任何应用层方案 |
| OS 层写盘：swap / zRAM / 系统快照 / 系统备份 | 用户已明确排除（`plan.md` D11）；我们只保证**消息**不被我们写盘 |
| 用户信息（账号、公钥、盐、通讯录、pin）的持久化 | 用户已明确允许（D13）。通讯录与 pin 存**客户端本地**（D13′=B′），服务端持久层只有账号数据 |
| 元数据抗分析（谁和谁、何时、多少、多长） | 需要 mixnet / P2P / 填充策略，属另一条产品线。**密文长度本身也泄漏信息**，v1 不做固定长度填充 |
| 推送通道元数据（APNs / FCM 得知「某账号在某时刻收到通知」） | 移动端后台的必然代价；缓解是载荷不含内容、文案泛化 |
| 群聊（Megolm/MLS）、多设备同步 | v1 非目标 |
| 匿名注册、抗审查、抗封锁 | v1 非目标 |
| 法律强制与合规（含地区性加密分发限制） | 需按目标地区单独评估 |
| 服务端可用性与抗 DDoS 的完整方案 | 仅做基本限流 |

## 8. 密钥生命周期

| 秘密 | 生成 | 存放 | 销毁时机 |
| --- | --- | --- | --- |
| 口令 | 用户 | 用户记忆 | —— |
| KEK | 每次启动：Argon2id(口令, 本地盐) | 仅进程内存 | 退出 / 空闲锁定 / 紧急擦除（`zeroize`） |
| 身份私钥 | 首次注册随机生成 | 本地 keystore（AEAD 密文） | rekey（改口令）或删除账号 |
| Olm 账号（含 prekey 私钥） | 首次注册随机生成 | 本地 keystore（密文） | 同上 |
| Olm 会话状态 | 握手时 | 本地 keystore（密文），随消息更新 | 同上 |
| 通讯录 / TOFU pin | 用户添加 / 首次联系 | 本地 keystore（密文） | 同上 |
| 消息明文（含图片） | 解密时 | 内存环形缓冲（≤10 条，图片另受 8MB 预算）+ UI 副本 | 超出 → 覆盖/淘汰；退出 → 清空；UI 副本不可控 |
| 消息密文 | 发送时 | 服务端内存（Valkey，禁用持久化） | TTL 24 小时 / D-ack 即删 / 组件重启 |

| **R6** | 依赖链风险（`vodozemac` 等） | 依赖版本 pin + 升级需过回归测试 | 引入 `cargo-deny` / 供应链审计 |
| **R7** | 队列组件是单点 | 接受（D9 方案 A） | 将来评估方案 B（分片 + 副本） |
| **R8** | 无固定长度填充，密文长度泄漏明文长度 | 接受 | 若需求提升，加填充层 |
| **R9** | ~~社交图谱落盘~~ | ✅ **已消除**（D13′=B′）：通讯录与 pin 只存客户端，服务端持久层无关系数据 | —— |
| **R10** | **身份不可恢复**：没有服务端密钥备份，设备丢失或 keystore 损坏 = 身份永久丢失 | 接受（“服务端零知识”的必然代价） | 后续：允许用户导出加密 keystore 自行备份；或可选的服务端密文备份（需重新讨论需求 1 的边界） |
| **R11** | **keystore 是新的一号攻击目标**：拿到文件即可离机爆破 KEK（盐与参数就在同目录） | 接受；靠 Argon2id 参数 + 口令强度约束 | 后续：可选的硬件绑定（平台 keystore 包裹一层）——但会牺牲跨设备导出能力 |
| **R12** | **图片解码是攻击面**：恶意图片可攻击解码器（解压炸弹、格式解析漏洞） | 缓解：格式白名单（拒绝 SVG/HTML/PDF）、解码前限制宽高与总像素数、显示与播放走平台能力 | 不引入不可信格式；跟踪 `image` 安全公告 |
| **R13** | **静默丢失是设计而非缺陷**：24 小时未取的消息永久消失，发送方无从得知 | 接受（G9/D22 的必然结果） | UI 必须事先说明；**不提供投递失败通知** |
| **R14** | 若压缩链路被绕过（异常路径直接发原图），EXIF/GPS 会泄露 | 缓解：发送图片的唯一入口是 `sme-media`，并用 I12 断言输出无元数据 | 代码审查 + 覆盖所有发送路径的单测 |
